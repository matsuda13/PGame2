# ショップアイテム効果適用設計

## 1. 概要

ショップで購入したアイテムの効果を、ゲーム進行中の適切なタイミングで適用する仕組みを定義する。

アイテムには単純な数値補正だけでなく、条件付き効果、累積成長効果、ゲームルールを変更する効果などが存在する。

そのため、アイテムごとに固有の処理を実装できる構造を採用する。

### 基本方針

- アイテムの効果は、共通インターフェースを実装したクラスとして表現する。

- 効果の発動タイミングや用途ごとに専用インターフェースを定義する。

- ゲーム進行役が、適切なタイミングでアイテム効果の適用を要求する。

- 所持アイテムの抽出と効果の呼び出しは、共通の管理機構が担当する。

- 個々のアイテムの存在を、ゲーム進行役が直接意識する必要はない。

- 新しい種類の効果を追加する場合は、必要に応じてインターフェースと呼び出し箇所を追加する。

## 2. インターフェース構成

### 2.1 共通インターフェース

すべてのアイテム効果に共通する親インターフェースとして `ItemEffect` を定義する。

```
public interface ItemEffect {}
```

`ItemEffect` はマーカーインターフェースとして使用する。

共通の処理メソッドは持たず、すべてのアイテム効果を同じ型として扱うために使用する。

例えば、以下のように異なる種類の効果を同一のコレクションで管理できる。

```
List<ItemEffect> effects;
```

### 2.2 用途別インターフェース

効果の発動タイミングや用途に応じて、`ItemEffect` を継承するインターフェースを定義する。

例：

```
public interface WorkRewardEffect extends ItemEffect {    void modifyReward(RewardContext context);}
```

```
public interface DayEndEffect extends ItemEffect {    void onDayEnd(GameContext context);}
```

各アイテム効果クラスは、必要なインターフェースを実装する。

一つの効果クラスが複数のインターフェースを実装してもよい。

なお、上記のメソッド名や引数の型は仮のものであり、具体的な定義は実装時に決定する。

### 2.3 インターフェースの分類

現時点では、以下の2系統を想定する。

**数値補正系**

既存の計算結果や計算条件に補正を加える。

例：

- 労働報酬 +10%

- 労働消費HP -10%

- 休憩回復HP +20%

- 生活費 -10%

補正値の計算には、ゲーム全体の補正ルールを適用する。

計算順序は以下とする。

1. 割合補正（合算して基本値に適用）

2. 固定値補正（確率の場合はpt）

3. 倍率補正

**イベント反応系**

ゲーム中の特定のタイミングで呼び出され、条件判定やゲーム状態の変更を行う。

例：

- 一日の終了時にHPを5回復

- 休憩するたび最大HP+1

- プルンを100消費するたび労働報酬補正が成長

- 戦闘勝利時に労働報酬補正が成長

この分類は設計上の整理であり、必ずしも共通の抽象クラスを2種類用意することを意味しない。

## 3. 効果適用の処理構成

### 3.1 責任分担

| 構成要素              | 責任                     |
| ----------------- | ---------------------- |
| ゲーム進行役            | 効果を適用するタイミングを決定する      |
| ItemEffectManager | 所持アイテムから対象の効果を抽出し、呼び出す |
| アイテム効果クラス         | 発動条件の判定と具体的な効果処理を実行する  |
| 所持アイテム管理          | 購入済みアイテムの情報を保持する       |

### 3.2 処理の流れ

労働報酬計算を例とする。

1. ゲーム進行役が労働報酬の計算を開始する。

2. `ItemEffectManager` に労働報酬補正の適用を要求する。

3. `ItemEffectManager` が所持アイテムを調べる。

4. `WorkRewardEffect` を実装した効果を抽出する。

5. 対象の効果クラスのメソッドを呼び出す。

6. 各効果クラスが必要に応じて補正を追加する。

7. 補正を集計し、最終的な労働報酬を確定する。

呼び出し処理の例：

```
public void applyWorkRewardEffects(RewardContext context) {    for (Item item : ownedItems) {        ItemEffect effect = item.getEffect();        if (effect instanceof WorkRewardEffect rewardEffect) {            rewardEffect.modifyReward(context);        }    }}
```

このコードは処理構造を示す概念例である。

実際の所持アイテムのデータ構造や、補正値の集計方法は別途決定する。

### 3.3 呼び出しと発動の区別

効果メソッドが呼び出されても、必ずしも効果が発動するとは限らない。

例えば「貯蓄の王冠」は、労働報酬計算時に毎回呼び出されるが、所持プルンが500未満の場合は補正を追加しない。

- 呼び出し対象の判定：`ItemEffectManager`

- 個別の発動条件の判定：アイテム効果クラス

## 4. アイテムと効果の関係

### 4.1 基本構造

各アイテムは、対応する効果を持つ。

特殊な処理が必要なアイテムについては、固有の効果クラスを用意する。

例：

```
ItemEffect  │  ├─ WorkRewardEffect  │    ├─ WorkRewardUpEffect  │    ├─ SavingsCrownEffect  │    └─ AdversityBraceletEffect  │  ├─ DayEndEffect  │    ├─ WaterBottleEffect  │    └─ HardshipMedalEffect  │  └─ RestCompletedEffect       └─ GrowingPillowEffect
```

### 4.2 単純な効果の共通化

すべてのアイテムについて専用クラスを作る必要はない。

例えば、無条件の割合補正を行うアイテムは、補正率を引数として受け取る共通の効果クラスを再利用できる。

一方、特殊な条件判定や状態変更を伴うアイテムは、専用の効果クラスとして実装する。

共通化の具体的な範囲は、実際の実装時に判断する。

### 4.3 複数インターフェースの実装

一つのアイテムが複数のタイミングで処理を行う場合、複数のインターフェースを実装できる。

例：「熟練の作業着」

```
public class VeteranWorkwearEffect        implements WorkRewardEffect, WorkCompletedEffect {    // 労働報酬計算時に累積補正を適用する    // 労働完了時に累積補正率を1%増加させる}
```

累積補正率のような変化する値は、ゲーム状態として保持する必要がある。

## 7. 購入済みアイテムの管理

購入済みアイテムの情報と、アイテム効果の処理は分離する。

### 購入時

1. 購入可能か判定する。

2. 代金を消費する。

3. アイテムを購入済みとして記録する。

4. 以後のゲーム進行で、そのアイテムの効果を適用対象とする。

原則として、購入時にプレイヤーの基礎ステータスを直接書き換える方式は採用しない。

ただし、将来、購入時に一度だけ発動する効果を追加する場合は、別途対応を検討する。

### セーブ・ロード

購入済みアイテムの情報を復元できれば、各タイミングで効果を再び適用できる構造とする。

ただし、以下のような累積成長効果については、追加の状態管理が必要になる。

- 熟練の作業着：累積労働回数または累積補正率

- ぷるぷる貯金箱：累積プルン消費量と補正率

- 戦士の胸当て：累積戦闘勝利回数または補正率

※現状セーブ・ロードは無いので気にしなくてよし

## 8. 設計上の注意点

### 8.1 ゲーム進行役とアイテムの疎結合

ゲーム進行役には、原則として特定アイテムの判定を直接記述しない。

避けたい例：

```
if (hasItem("職人の道具箱")) {    reward *= 1.1;}
```

代わりに、効果管理機構に処理を委譲する。

これにより、既存の処理タイミングに対応するアイテムを追加する際、ゲーム進行役の変更を最小限にできる。

### 8.2 補正計算の統一

数値補正系の効果は、可能な限り補正値を集計してから計算する。

各アイテムが個別に最終値を乗算・加算すると、適用順序によって結果が変わる可能性がある。

ゲーム全体の補正ルールと矛盾しない仕組みを用意する。

### 8.3 新しいルールへの対応

既存のインターフェースで表現できない効果が登場した場合は、新しいインターフェースと呼び出し箇所を追加する。

すべての効果を単一の `apply()` に押し込めることはしない。

### 8.4 過度な汎用化を避ける

現時点で存在しないアイテム効果を想定して、大量のインターフェースや抽象クラスを先行実装しない。

実際に必要となった効果に合わせて拡張する。

## 10. まとめ

ショップアイテムの効果適用には、**用途別インターフェースと共通の効果管理機構を組み合わせる方式**を採用する。

基本構造は以下とする。

```
ゲーム進行役    │    │ 適切なタイミングで効果適用を要求    ▼ItemEffectManager    │    │ 所持アイテムから対象効果を抽出    ▼用途別インターフェース    │    │ 対応するメソッドを呼び出す    ▼アイテム効果クラス    │    │ 条件判定・補正追加・状態変更    ▼ゲーム処理へ反映
```

共通の親である `ItemEffect` は、現段階では空のマーカーインターフェースとする。

この構成により、単純な数値補正から特殊なルール追加まで、アイテムごとに固有の処理を実装できるようにする。

一方で、初期段階から過度に汎用化することは避け、必要な効果に応じて段階的に拡張する。



## 11. 確定事項と実装（2026-11-03追記）

この節は、上記の概念例・未確定事項に優先する。購入機能と効果を実装する。

### 効果と補正計算

- `effect.GameEffect` を共通の親とし、`item.ItemEffect` と `event.EventEffect` が継承する。
- 用途ごとの処理は `GameEffect.Numeric / DayStart / WorkCompleted / RestCompleted / PlunSpent / DayEnd / ActionAvailability` で分ける。数値補正の対象は `EffectTarget` で識別する。
- `GameSession` が必要なタイミングでイベント管理・アイテム効果管理へ要求する。特定アイテム名の判定をゲーム進行に埋め込まない。
- 計算ごとに新しい `common.ModifierContext` を作る。労働効率・イベント・アイテムの全補正を収集してから基本値へ適用する。
- 割合と固定値は加算、明示倍率は乗算で蓄積する。計算順は **割合→固定値/pt→倍率**。基本1、プロテインの雨+100%、教本+1なら結果は3。
- 画面表示・実行可否の照会は状態を変更しない。労働回数などの成長は完了通知でのみ更新する。
- 逆境の腕輪は労働前の現在HPと最大HPを参照する。割合は分子・分母のまま収集し、途中では除算しない。最終結果だけ循環小数になる場合はDECIMAL128で表現し、資源反映時に最終値をfloorする。

### 日終了・最大HP

1. 小目標の評価と報酬付与。
2. アイテム補正。直前のHP・最大HP・所持金を共通の読み取り専用スナップショットにする。全効果の発動条件をこの状態で判定し、回復・成長量をまとめて反映する。
3. 補正後の生活費を処理。
4. 死亡判定。死亡時は日付を進めず、翌朝処理を行わない。
5. 生存時のみ日付更新と翌朝処理。

- 水筒と勲章を所持し最大HP100・HP48なら、両方が発動し、生活費処理前に最大HP101・HP54となる。購入順に依存しない。
- 最大HPの増加分は現在HPにも加える。枕は休息の回復後に成長する。
- 回復魔法の上限、朝の全回復、画面のHPゲージも現在の最大HPを参照する。
- 生活費不足時は残金を失い、HPを50失う。貯金箱所持時の生活費は45。

### 支出・累積・行動

- あらゆるプルン減少を、丸め後の実際の差分で累積消費に含める。購入・生活費・回復魔法・生活費不足時の残金没収も対象。収入は含めない。
- 支払いが先、所持登録が後。ぷるぷる貯金箱自身の購入代金は取得前なので対象外。取得前の過去の消費も含めない。
- 100未満の消費は持ち越す。一度に複数の100を消費した場合も対応する。
- 熟練の作業着は完了した労働で成長し、その労働の報酬には遡及しない。
- 金の砂時計は残り時間が正の場合だけ時間不足を許可し、消費後の時間は最低0にする。資金不足・死亡は許可しない。

### 購入状態・商品一覧

- `item.Item` の列挙名を商品IDとする。共通の無条件補正は再利用し、条件付き・累積効果は専用クラスにする。
- 所持品と効果インスタンスは `ItemEffectManager` がゲームごとに保持する。閉店・日付変更では保持し、最初からやり直すと全て初期化する。セーブ・ロードは対象外。
- 常設7種類は各500 PLN、行商人6種類は各1000 PLN。行商人は1日目と10の倍数の日に利用でき、その日の初回表示時に未所持から重複なしで最大3種類を抽選する。
- 同じ来訪日に開き直しても商品は同じ。購入済み商品もその日の一覧に残し、次回来訪の抽選から除外する。未所持が少なければ残りの種類だけ表示する。
- 求人掲示板・戦士の胸当ては前提機能が未実装のため保留。旅人のお守りは常設ショップ仕様に従い対象外。これらは販売しない。
- 購入可能かを押下時にも再確認する。商品選択だけでは購入せず、購入後も画面を維持する。所持金・購入済み表示・ボタンを即時更新し、閉店時にはメニューの補正値・HP上限・実行可否を更新する。
